# Version 3 run procedure

New CLI runs default to workflow version 3. Existing runs without a version remain version 2; `init --workflow-version 2` supports historical reproduction. Storage schema 1 remains readable. Requirement IDs come from the checkout's `workflow/specs/ROLE-REVIEWER.md`; isolated test checkouts without that specification retain the original six-ID fixture vocabulary.

The coordinator invokes these commands at actual boundaries. The CLI cannot observe agent launches, retrieve hidden token counters, authenticate identities, or assess scenario quality. Independent reviewers still inspect the matrix and implementation.

## 1. Initialize and prepare dispatch

Use `workflow.py init`, `expect`, and `start` from the [CLI reference](README.md). Register planned agent/stage/attempt records before dispatch; start recording before edits. Register disjoint `assignment` ownership and dependencies before binding acceptance cases.

For commands after initialization, place `--run logs/<name>/reviewer/<run-id>` before the subcommand. Use `--repo <checkout>` before it when selecting an authorized alternate checkout.

Keep one canonical run at `logs/<name>/reviewer/<run-id>/state.json`. Put disposable JSON inputs in `inputs/`, generated handoffs in `handoffs/`, and optional derived Markdown in `reports/` under that run. Successful ingestion retains canonical data or provenance, so inputs need not be copied into handoffs. Resource measurements live in state records. If using the separate shared resource recorder, its interval directory contains interval records only: keep usage inputs and derived reports elsewhere.

## 2. Register executable checks

Register each trusted contract with `check-register --input inputs/<check>.json`:

```json
{
  "id": "environment",
  "kind": "preflight",
  "argv": ["python", "-B", "-c", "import sys; sys.exit(sys.version_info < (3, 11))"],
  "paths": ["workflow/reviewer/scripts"],
  "depends_on": [],
  "resources": [],
  "environment": [],
  "database": null,
  "timeout": 30
}
```

This example checks the tooling runtime only. Discover actual build/static/unit/integration/browser commands. Acceptance-check argv must select named tests exercising its mapped cases. Kinds are `preflight`, `fixture`, `unit`, `integration`, `browser`, `build`, and `static`. Each check declares concrete source/configuration/fixture paths and already registered dependency check IDs. Dependencies contribute scopes to downstream snapshots and selection. Include shared authorization, contracts, migrations, package manifests and lockfiles where relevant. Revised contracts get new IDs; previous evidence remains historical.

`environment` contains required variable names, never values. Keep credentials out of argv and JSON. Database checks additionally declare `database: {"environment": "TEST_DATABASE_URL", "name": "specsentry_test"}`. List the variable in `environment`; its PostgreSQL URL must identify exactly that explicitly provisioned `*_test` database. This validates the name, not server safety or connectivity. Use an authorized disposable database and an actual connection/migration preflight command. Database-backed plans also require an executable `fixture` check. Validate normalized accounts, required roles and cleanup coverage for affected foreign-key tables in product-owned fixture code before dependent tests.

Build and browser checks automatically acquire the `build` lease. Database contracts acquire `database`; explicitly declare it for any other check touching the shared database. Other named resources can protect profiles or servers. Leases at `logs/.reviewer-verification-locks/` serialize checks across runs in this checkout, fail promptly on contention, and release on exit. Checks must use this runner to participate. Separate worktrees require separate outputs/databases or external coordination. Before removing a crash-left lease manually, inspect its PID/run/check and confirm no owner or child process remains; leases are never stolen.

## 3. Compile acceptance and race cases

Call `matrix --input inputs/matrix.json` before dispatch. One case looks like:

```json
{
  "cases": [{
    "id": "notice-open-race",
    "requirement": "REQ-REV-008",
    "kind": "concurrency",
    "owner": "notifications",
    "check": "notice-races",
    "scenario": "Opening an old revision races a newer notice",
    "preconditions": "Reviewer is assigned and revision 1 is open",
    "events": ["Open revision 1", "Commit revision 2 and its notice"],
    "expected": "The revision 2 notice remains unread; only the opened revision notice is acknowledged"
  }],
  "not_applicable": {}
}
```

This fragment is incomplete: add a `normal` case for every run requirement and task coverage for `authorization`, `boundary`, `lifecycle`, `concurrency`, and `rollback`. Where a risk kind does not apply, put its nonempty rationale in `not_applicable`, keyed by kind. Coverage and waiver are mutually exclusive. Cases have exactly the illustrated fields, unique IDs, existing assignment owners and registered executable checks. Concurrency cases name at least two competing events. Add separate cases for critical orderings and boundary states. Expected transactional outcomes cover business state, audit and required notifications together. The tool cannot infer omitted semantic combinations.

Revisions append matrix history and require `--reason`. Retain the original plan and review waivers/revisions independently. Run `verify --check <id>`; preflight/fixture checks are automatically included. `readiness --assignment <id>` checks matrix presence, current passing prerequisites and current successful completion of assignment dependencies.

Version 3 `start --stage implement` and `start --stage fix` require `--assignment <id>` owned by the agent and enforce readiness before creating a record. Foundation work must complete before dependent dispatch. A rejected dispatch does not start work; work that actually fails or is interrupted needs a recorded attempt.

## 4. Verify settled changes

`verify --check <id> --check <other-id>` executes selected checks and dependencies in order, visiting shared prerequisites once. Prefer one batch over separate forced invocations. `verify --changed <path>` selects checks whose own or dependency scopes overlap explicit changed paths; repeat for multiple paths. `--select-only` prints the selection. No matching checks is an error. Supply the complete changed-path set, including deletions and shared contracts; automatic Git change discovery is not implied.

Only the latest passing, non-superseded evidence with current selected hashes and HEAD/base is reusable. Environment presence is checked even on reuse. Use `--force` after database resets, setup/migration changes, server/browser restarts or suspected nondeterminism: source hashes cannot establish unchanged external state. Readiness records a preflight outcome, not continuous health monitoring. Prerequisite failures stop dependent execution. Failures remain recorded and block completeness until explicitly superseded by passing replacements using `supersede`.

Source snapshots exclude dependency/cache trees (`node_modules`, `.venv`, `__pycache__`, `.next`, `.pytest_cache`), browser output (`playwright-report`, `test-results`), logs and conventional secret paths. Include manifests and lockfiles. Freeze relevant writers during collection. Command IDs are reserved under a short writer lock, execution runs outside it, and results finalize under a fresh lock. Other agents can record progress during long checks. A crash leaves unfinished evidence: inspect/terminate remaining processes, create a new attempt/ID, then explicitly supersede the abandoned result after its replacement passes. Existing [command limits](README.md#3-snapshot-and-run-explicit-checks) still apply.

For direct or delegated integration that permits wiring edits, use `start --stage integrate --changes-code`. That agent is treated as a code author for review independence, and its completed interval participates in owner-fix closure timing. Inspection-only integration does not need this flag. Integration output uses the ordinary handoff and `finish` commands; `complete` remains for implementation/fix assignments.

## 5. Complete once and generate views

Call `complete --id <boundary-id> --input inputs/completion.json` after successful scoped checks:

```json
{
  "assignment": "notifications",
  "record_id": "rec-RETURNED-BY-START",
  "snapshot_id": "settled-notifications",
  "commands": ["verify-RETURNED-BY-VERIFY"],
  "changed_paths": ["src/server/src/notifications/notifications.service.ts"],
  "summary": "Implemented revision-specific acknowledgement",
  "risks": "Independent integration review remains pending",
  "next_action": "Review lifecycle race cases",
  "references": ["workflow/specs/ROLE-REVIEWER.md"],
  "unavailable_reason": "Per-stage usage counters are not exposed"
}
```

Use actual IDs and discovered source paths. Completion requires passing current commands, a fresh snapshot covering declared changed paths, matching assignment/agent/resource identity, owned files and current prerequisites. One transaction finishes the running resource record and derives a seven-section handoff from canonical completion data. Rejected input leaves the record running; each record can complete once. Use ordinary `finish --status failed|interrupted` for unsuccessful attempts. Assignment, design and review handoffs remain available through `handoff create`.

Import directly attributable final counters with `usage` when exposed; otherwise completion records explicit unavailable reasons. Existing one-import rules also allow later telemetry to fill missing values. Read-only workers return structured content for the coordinator to persist; they need not produce duplicate Markdown reports.

After independent review, `completeness` additionally requires current executable evidence for every latest matrix case and current successful completion of every implementer assignment. Low-level `command` evidence alone cannot satisfy a matrix case: `verify` binds execution to the check contract. Scenario quality, changed-path completeness, fixture assertions and environment isolation remain review responsibilities.

Finally `report` prints a derived Markdown report with assignment/completion status, acceptance cases, findings, evidence index, consistency gaps and resource summary; exit 1 indicates an incomplete run. `report --format bundle` emits one JSON object with `consistency` and `markdown`, both from the same validation. Use this instead of consecutive unchanged `completeness` and `report` calls when both views are needed. Save under `reports/` if useful and link canonical state from the prompter-named log. Rendering creates no extra canonical record. Preserve failed/interrupted attempts and supersession links under the [retention policy](README.md#7-evidence-efficiency-and-retention).

## 6. Refresh evidence and close findings

Keep application, requirement/contract and documentation snapshots separate by explicit `--path` selections, with relevant dependencies included. Documentation changes still need review; unchanged application checks remain reusable only when their selected sources and contracts remain current. Scope selection is an agent/reviewer responsibility, not inferred from file extensions.

When external state or revised check contracts require rechecking **identical selected content**, finish the actual verification, supersede replaced commands, then refresh the existing completion:

```powershell
python -B workflow/reviewer/scripts/workflow.py --run logs/ngkhengyang/reviewer/example completion-refresh --id evidence-2 --from implementation-1 --snapshot settled-application --command verify-NEW-ID --reason 'Revalidated after test database reset'
```

Repeat `--command` for all required passing evidence. Refresh retains the original resource record and timing, appends a linked completion/handoff and records the reason; record the actual administrative work under `document`/`close`. It requires the old and proposed snapshots to be current and identical (paths, content, HEAD/base and diff), current prerequisites, check coverage of every declared changed path, and no newer implementation/fix attempt. Changed content needs the normal owner fix/completion and independent review. Refresh neither closes findings nor supersedes old evidence automatically; retain explicit successor links. Retrying the exact same refresh ID/payload validates and reuses it without another completion or handoff.

After an assigned independent reviewer has completed revalidation, prepare a batch file:

```json
{
  "reviewer": "verifier",
  "record_id": "rec-SUCCESSFUL-REVALIDATION",
  "snapshot_id": "post-fix-application",
  "findings": [
    {"id": "F-001", "evidence": ["logs/ngkhengyang/reviewer/example/reports/revalidation.md"], "reason": "Fix and regression verified"},
    {"id": "F-002", "evidence": ["logs/ngkhengyang/reviewer/example/reports/revalidation.md"]}
  ]
}
```

Run `finding close-batch --input inputs/closures.json`. Each entry is checked against the existing independence, timing, reopen and current-snapshot rules before a single atomic state update. Any invalid entry leaves all findings unchanged. Exact retries of already applied entries revalidate their evidence and add no history; a changed closure requires explicit reopening and fresh review. Batch one reviewer/record/snapshot at a time. Single-finding `finding update` remains supported.

Read operations (`readiness`, `completeness`, `report`) cache state, distinct scope manifests and check results only within that invocation. Every selected scope and used artifact is checked again at the return boundary, along with run state. Concurrent changes fail the operation; settle writers and retry. No cache persists across commands, code edits, external checks or mutations. Artifact hashes and traversal/redirection guards remain in force; caching does not certify environment health or review quality.
