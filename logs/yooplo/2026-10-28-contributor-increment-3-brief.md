## Current implementation and dependency findings

- Existing ProposalLifecycleService creates/list/reads/saves private working drafts. It locks account then session through businessTransaction, locks proposal with ProposalsService.lockRoot, rechecks expiry before transaction completion, and appends DRAFT_CREATED/DRAFT_SAVED through ActivityService. Save requires DRAFT, null firstSubmittedAt/currentRevisionId/releaseAttachmentRef and matching version. No delete method/controller/DTO/tombstone exists. No submit controller exists on this branch; submitted foundation records/services support Reviewer work, not verified Contributor submission.
- WorkingRevision.content is the whole private JSON (title, summary, problem, constraints, expected behavior, diff, criteria/stable keys, evidence/IDs). Submitted ProposalRevision/AcceptanceCriterion/TestEvidence/CriterionEvidenceLink are separate immutable rows. Root title is a placeholder for ordinary private creation, but deletion must remove the entire root regardless of placeholder convention.
- Prisma alone is insufficient evidence: revision_cycle SQL defines WorkingRevision.proposalId ON DELETE RESTRICT even though its Prisma model has no relation. ProposalActivity has RESTRICT root/revision/assignment FKs and an unconditional append-only UPDATE/DELETE trigger. Every normal draft already has activity, so straightforward root deletion fails. SecurityEvent is operational evidence with extra fields and90-day retention; it is not the durable minimal tombstone.
- Existing detail/editor/list routes and RTL/PostgreSQL/Chromium suites can be extended. Existing save contract and auth/session-generation guard should be reused. No schema copies, Reviewer branch import, new lifecycle state, withdrawal endpoint or AI work are needed.

## Smallest proposed service and persistence change

Wire: `DELETE /api/proposals/:id`, JSON `{expectedVersion, confirmed:true}`, same-origin session cookie and CSRF header; bodyless204. Client cannot supply actor, timestamps, state, owner, reason or arbitrary content. Reuse opaque ID, bounded version validation, safe error envelope and existing forbidden/not-found/conflict distinctions. No Idempotency-Key required by the approved delete policy; do not add command-response persistence for this operation.

Transaction proposal, pending shared persistence agreement:

1. IdentityGuard authenticates/role-checks/CSRF-checks; controller validates strict ID/body. businessTransaction locks/revalidates account/session; lockRoot serializes lifecycle access. Check owner before disclosing lifecycle, then expectedVersion and eligibility.
2. Require DRAFT; firstSubmittedAt/currentRevisionId/currentAssignmentId/releaseAttachmentRef all null; no ProposalRevision or assignment/history dependencies, even if root markers are inconsistent. Require a WorkingRevision. Non-DRAFT/ever-submitted/attached/inconsistent graph fails closed without deleting or repairing history. Exact conflict mapping for inconsistent WorkingRevision absence should match existing404 behavior unless coordinated otherwise.
3. Insert DraftTombstone, purge only eligible private draft activity via a narrowly guarded database path, delete WorkingRevision, delete root, recheck session expiry, commit all together. Order must respect FKs. No intermediate state is published; tombstone failure, activity cleanup failure, delete failure or expiry rolls everything back. Restricted rejection audit may remain separately, as existing businessTransaction specifies. Do not call ActivityService.append for a deletion event attached to the root being removed.
4. Tombstone physical proposal: proposalId primary key (no FK to deleted root), actorId, action constrained to DRAFT_DELETED, timestamp from database; append-only. Only four fields, no technical event ID needed. Actor FK/retention details need owner confirmation. No content/title/diff/criteria/evidence, reason/summary, copied owner/version, IP/session/credential/correlation fields. It is not exposed through proposal/detail/list/timeline routes. Operational safe read/rejection SecurityEvents remain under their separate90-day policy; they must not become a second permanent business tombstone.

| Relationship | Proposed deletion effect |
| --- | --- |
| ChangeProposal | Remove whole eligible root; do not retain a hidden empty DRAFT or invent DELETED state |
| WorkingRevision | Remove row and entire JSON, including unexposed criteria/evidence; physical RESTRICT means explicit delete before root |
| Private ProposalActivity | Existing DRAFT_CREATED/DRAFT_SAVED only, null revision/assignment, eligible never-submitted root: proposed removal under guarded exception; unresolved append-only policy/migration gate |
| DraftTombstone | Insert exactly one minimal durable non-content row, transactionally; no content read API |
| ProposalRevision and its criteria/evidence/links | Must be absent for deletion; never delete, update or cascade submitted history |
| ReviewAssignment, coverage, findings/events, decisions, ReviewIdempotency, notifications, ApprovalInvalidation | Must have no linked history; reject unexpected relationships rather than cascade or repair. Preserve immutable constraints and provenance |
| UserAccount/AuthSession, unrelated proposals/history/security evidence | Remain; current safe operational rejection/read events retain separate policy; no new success payload logs |

Migration acceptance conditions: preserve every submitted-content and review-history guard; preserve immutable activity on all submitted or historical roots; any private cleanup exception must verify eligible locked root, no submitted/history dependents, only allowlisted null-revision/null-assignment draft events, and matching minimal tombstone in the same atomic operation. A freely settable session flag, blanket cascade or dropping the general trigger is unacceptable. A guarded database routine/trigger and final consistency enforcement are options for the persistence owner to design/review, not an agreed interface or an implemented control. Do not edit any old migration.

Concurrency: use the same lifecycle root serialization as save and future submit. At a single expected version, edit-first makes delete stale409; delete-first makes save/read absent404. Delete/delete produces one204/tombstone and one404, no duplicate tombstone. Submit-first makes delete ineligible/stale409; delete-first prevents submit404 with no revision. Actual Contributor submit integration is unavailable: design the lock-barrier future test, use clearly labelled fixture transaction for structural checks, and do not claim cross-role submission verified. Delete does not increment a version on a root that ceases to exist; maximum valid expectedVersion can be accepted if it exactly matches, pending confirmation, with max+1 invalid422.

## UI proposal

Pass existing session context into DraftDetail; show delete on own private DRAFT detail, not editor/list bulk actions. Server remains authoritative because detail DTO lacks ever-submitted markers. Inline labelled confirmation region/form states permanent deletion and identifies the escaped draft title; separate Cancel and explicitly labelled Delete buttons; no text reason. Keyboard access, logical heading/status, visible focus, initial safe focus and cancel focus restoration are required. Busy state prevents duplicate delete and conflicting local navigation/actions; success204 clears content and returns to fresh owner list with status and empty state if appropriate.

409 retains displayed content, disables stale confirmation and offers explicit reload/reconfirmation. For network loss/5xx/ambiguous completion, never assume success or automatically resend: disable delete until explicit authorized GET draft recheck. Found: reload current content/version and require fresh confirmation;404: show safely that draft is no longer available and return to list (do not claim this request necessarily deleted it);401: invoke current auth-generation handling;403: clear protected content/show safe denial; failed recheck retains uncertainty with bounded user retry. No browser-storage persistence of sensitive content. Route/auth-scoped callbacks must prevent old responses changing another proposal/session; current-session401 must still invalidate current login when appropriate.
