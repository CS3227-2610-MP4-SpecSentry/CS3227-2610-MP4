## Findings

1. **SO-001: prompt-only generation does not reliably satisfy the existing contract.** A fresh Llama baseline using the saved-draft synthetic context returned HTTP 200/stop with an empty objective. JSON-object mode also returned an empty objective and zero acceptance criteria. A fresh Qwen baseline returned four ambiguities, exceeding the existing maximum of three. These are new reproductions; the earlier application failure did not retain field diagnostics, so its exact invalid field cannot be reconstructed.
2. **SO-002: schema-constrained generation is supported in these observed routes.** Both `llama3.1:8b` and `qwen3.6:35b` accepted `response_format: {type: "json_schema", json_schema: {name: "contributor_draft", strict: true, schema: ...}}`. Both rejected an invalid JSON Schema type with HTTP 400. Both followed a schema canary fixing the objective and tightening array counts despite conflicting system-prompt instructions. Together these checks provide stronger enforcement evidence than HTTP 200 alone. They do not establish all JSON Schema keyword semantics or future routing behavior.
3. **SO-003: the bounded schema matrix passed.** Ten ordinary-context schema requests passed the unchanged production envelope decoder and strict Contributor runtime schema: the initial saved-draft request per model, then saved-draft, multilingual, delimiter/injection and 4,000-unit near-cap inputs per model. Both additional canaries passed. Ordinary-context schema latencies ranged from 1,629 to 3,917 ms; every completed check remained within its 20-second deadline. There were no retries or output repairs. This small sequential sample is not a reliability percentage, load benchmark or usefulness evaluation.
4. **SO-004: JSON-object mode is insufficient.** It passed Qwen once but failed Llama's required nonempty fields. Syntactically valid JSON does not establish schema compliance.

## Method and evidence

- Inspected the current production prompt, transport, strict envelope decoder, runtime schema, synthetic verifier, actual browser acceptance context and applicable specifications. Current transport sends no `response_format`.
- Read the five user-supplied SoCLaaS PDF snapshots. The only `response_format` mentions found concerned audio transcription, not chat JSON Schema. The official API web page was inaccessible through the browsing tool. Therefore chat-schema support here is **empirical provider evidence**, not a claim that the snapshots document it. The first PDF extraction failed on sandbox read permissions; an escalated read succeeded. No new dependency was installed.
- Used an isolated probe wrapping the existing bounded production HTTPS transport's fetch call to append the experimental request parameter. Prepared messages and decoding reused production exports. Exactly the approved endpoint, redirect rejection, response byte limit, 800-token cap, no streaming, no tools, `reasoning_effort: none` and total deadline were retained. The ordinary `.env` live switch was asserted false. Credentials were read locally and never printed or written to evidence.
- Two preplanned stages: eight capability requests, followed by ten boundary/canary requests. No automatic retries. Stop on HTTP 401/403/429. Synthetic inputs only; no database, server, browser or private user records were used. The canary deliberately changes its synthetic system instruction and schema; it is separate from product-context acceptance.
- Safe diagnostics record fixed field names, string lengths, array counts, issue codes/allowlisted paths, response status, latency and valid provider usage. Raw response bodies, generated strings, provider error text and reasoning were not retained. Decoder acceptance includes all existing finish/refusal/tool/strict-JSON/schema checks. A self-check confirmed invalid array counts fail and generated sentinel text is absent from serialized diagnostics.
- [Capability results](structured-output-investigation/verification/capability-results.json), [boundary results](structured-output-investigation/verification/boundary-results.json), [probe artifact](structured-output-investigation/verification/probe.cjs). The artifact includes an explicit `--live` guard added after the live investigation; run from the repository root against built server/shared output, with `--boundaries` selecting the second matrix. Running it incurs real provider requests. Its final guard was tested without making further requests.
- An offline assertion check verified 8/10 request counts, all ten ordinary schema passes, both canaries, both invalid-schema 400s, known input-token margins and deadline bounds. Probe syntax and `git diff --check` passed.
- Provider-reported known subtotal across 16 responses: 6,212 input + 2,262 completion = 8,474 tokens. Both HTTP 400 responses had unknown usage; cache usage was unknown throughout. These are product-provider metrics, not development-agent token usage, and not a complete billing total.

## Recommended implementation and remaining checks

Use a fixed server-owned JSON Schema for **Contributor requests only**, with the same five required fields, `additionalProperties: false`, string bounds and array bounds as the existing runtime contract. Extend the transport request at the Contributor call site; do not apply this schema to Reviewer or Maintainer requests, accept browser schema overrides, relax validation, truncate/repair output, or retry validation failures. Keep the runtime validator: JSON Schema `minLength: 1` still permits whitespace-only text, and provider schema support does not replace strict parsing, response metadata checks or business authorization.

The normal schema parameter serializes to 749 UTF-8 bytes, separately recorded from the existing message-only input-unit counter. The measured prompt token counts for the same context were unchanged across baseline/JSON/schema modes (346 Llama, 363 Qwen), and all observed margins passed. This does not prove how every backend accounts for schema grammar. Before integrating, explicitly review schema overhead against the conservative admission policy and context reserve; do not silently treat extra request data as covered or claim exact-token proof. Version the generation configuration/evidence so schema-mode results are distinguishable from earlier prompt-only results.

The smallest implementation reaches the Contributor gateway preparation/call, shared internal transport request type, fixed schema and HTTPS serialization, focused transport/gateway tests, synthetic/live acceptance harnesses and relevant specifications/guides. Shared gateway/transport changes require the existing ownership coordination and independent security/acceptance workflow. No persisted business schema or migration is needed for this investigation.

After integration, rerun the authenticated saved-draft browser path through actual application wiring, including explicit selection/application/save, safe usage accounting and manual fallback. That successful live application path remains **unverified**. Provider key limits/data handling, other role evaluations and deployment gates also remain unresolved. This investigation does not authorize production activation or waive them.
