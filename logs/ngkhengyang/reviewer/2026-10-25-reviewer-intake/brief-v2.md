## Client authorization generation

Frontend owns a single authorization generation shared by session checks and protected Reviewer requests. Every transition that invalidates access (401, authoritative assignment denial, expired session, logout, account/role change or failed session verification that clears the session) invalidates outstanding response generations before clearing protected state. A request captures the relevant authorization/proposal/assignment/revision generation and may commit data only when all remain current. A session-check 200 that began before a later terminal 401/error may not remount protected content. Aborting is helpful but insufficient; commit checks are mandatory after parsing too.

Do not persist sensitive responses in local/session storage or durable browser caches. On navigation/drop/observed loss clear detail/history/activity and ignore all older response generations. Revalidate on focus; render login or access-loss feedback without stale content. This does not promise retracting already delivered data or real-time revocation in another idle browser tab; server reauthorization protects every later request and response authorization is linearized within its transaction.

Required frontend checks: hold two session requests, resolve the newer 401 (and separately verification error) before an older 200, then assert session/protected workspace stays cleared; hold detail/history/activity responses across successful drop, navigation, expiry and account change, then assert stale responses cannot restore content. Backend checks still prove full-content requests fail after committed access loss. Existing App.tsx session race is an implementation control to fix later, not a fix already delivered.

## Bounded revision/history and wire values

Replace v1's embedded submitted-revision index: detail returns exactly one authorized selected immutable submitted revision plus current root/assignment metadata. Add `GET /api/proposals/:id/revisions?limit=...&cursor=...` for same-proposal submitted revision summaries, default 20/max 100. Order revision number descending then ID ascending; summaries contain only revision ID, number, submittedAt and bounded summary. Reauthorize current assignment and account before each page and each detail/link request. No draft revisions, cross-proposal IDs, hidden aggregate counts, finding/AI metadata, or full diff/evidence in revision-list pages. Use `{items,nextCursor}`; frontend loads further pages explicitly. Activity remains 50-entry chronological pages.

Proposed implementation bounds, supplementing existing product field limits: opaque identifiers 1–128 printable ASCII characters, preserved exactly without trimming (do not infer authorization or semantics from shape); generated IDs use existing UUID conventions. Versions are integers 0..2,147,483,647, matching Prisma/PostgreSQL Int; reject overflow rather than wrap. Cursor wire string is 1–2,048 ASCII characters, with a versioned encoding and decoded representation at most 1,536 bytes; reject invalid encoding, excess/unknown decoded fields, invalid timestamp/ID/number boundaries and out-of-range lengths. Cursors carry ordering position only, never viewer or access grants. Any scope/filter fields must match the current request; do not retrieve an unscoped global anchor. An unsigned syntactically valid changed position is harmless navigation, not an integrity claim; invalid/scope-mismatched/oversized cursors fail safely. Limit is integer 1–100, default 20; timeline page size fixed 50. Age bounds are integers 0–365,000 days with min<=max; reject nonrepresentable timestamp arithmetic. These are engineering choices within the bounded-query contract, not claims that existing product specs already name these constants.

Prove byte/code-point boundaries, unknown parameters, invalid cursors, overlapping timestamp/ID sort boundaries, cross-scope cursor reuse, history pagination and revoked-access paging. Strict response schemas and explicit server selects whitelist all representations. Selection and transaction authorization must precede relation loading; no generic serialize-everything mapper.

## Account and transaction identity

HTTP guard remains necessary. Services additionally carry the authenticated account ID and session's account version into the authorization transaction, reread/lock account, and compare enabled/current role/account version before protected retrieval or mutation. Disabled or version-changed accounts cannot rely on the guard's earlier result. Apply the same actor-account-then-proposal lock order across claim, drop, read and disable participants; multi-root disable sorts proposal IDs. PostgreSQL constraints protect active uniqueness and current-revision/proposal association. No application operation can mutate submitted snapshot fields.

## Ownership controls and design gate

One backend implementer owns claim/drop, proposal access, activity append, account-disable integration and real DB race/rollback tests, keeping transaction invariants under one owner. Foundation owns schema/migration/generated Prisma and browser contracts first; main approves resulting contracts before backend/frontend start. Frontend owns all client code and tests so the App.tsx generation fix is within its write set. Main owns shared module/config/script integration and evidence. All participants preserve others' edits; independent security and implementation reviewers remain read-only.

No scope expansion into Contributor writes, live AI, product finding/coverage/decision writes, notifications, releases or deployment. A future approval record is not fabricated to make intake tests pass: frozen-state fixtures test denial and disable noninterference without claiming effective-approval acceptance. Security re-review must assess these refinements before the checkpoint is declared ready to dispatch; the user-requested pause still prohibits actual dispatch.
