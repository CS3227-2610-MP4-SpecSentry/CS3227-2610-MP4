## Goal, sources, and scope

Deliver an authenticated Reviewer journey: browse safe unassigned pool metadata, claim, inspect the immutable submitted revision, see own assignments and authorized activity, drop, and allow another reviewer to claim. Development/test fixtures supply submissions; no Contributor write API/UI is included.

Authorities: [product lifecycle/authorization/invariants](../../../../workflow/specs/PRODUCT-SPEC.md), [Reviewer requirements/acceptance scenarios](../../../../workflow/specs/ROLE-REVIEWER.md), [integration entities/routes/errors/limits/concurrency](../../../../workflow/specs/INTEGRATION-SPEC.md), [shared requirements/activity/accessibility](../../../../workflow/specs/SHARED-REQUIREMENTS.md), [architecture](../../../../docs/Architecture.md), [Reviewer implementation procedure](../../../../workflow/reviewer/IMPLEMENTATION.md).

Deferred: findings/coverage/decision writes, assigned severity filters, revision submission/notifications, AI, approvals/revocation/releases, complete Contributor and Maintainer representations, full production performance/accessibility/deployment acceptance. Existing product requirements are retained, not relaxed.

## Current implementation and proposed components

Existing: NestJS identity, fresh account checks in the guard, CSRF, role decorators, PostgreSQL/Prisma, security events and pruning, React authenticated role landing pages, unit/HTTP/PostgreSQL/browser tooling. Proposals, Reviews, Activity are registrations only. Current schema has accounts/sessions/throttles/security events, no business tables. Account disable presently updates account/version/security event only.

Foundation adds only the physical entities needed here: proposal lifecycle/current revision/version, immutable submitted revision, criteria (stable key, required default true), optional plain-text evidence, revision-scoped historical assignments with active pointer/version, append-only business activity. Keep original submission time separate from latest revision time. Preserve chronological historical assignments on drop/reclaim. Add no public fixture/submission creation route. Business activity storage is separate from 90-day operational security pruning. Future finding/coverage modules must attach to preserved revision/assignment IDs; this increment creates neither fake assessments nor decision controls.

Proposals owns proposal lifecycle and submitted-content retrieval through narrow transaction-aware interfaces. Reviews owns assignment commands/queries. Activity owns the allowlisted projection. Identity disablement calls a narrow transaction-aware release operation; the same database transaction contains account disable/version increment, assignment release, root transitions, and audit/activity.

## Proposed wire contracts

Common conventions: browser-safe strict Zod schemas in `src/shared/src/contracts/reviewer.ts`, re-exported in index; IDs opaque nonempty bounded strings, versions nonnegative integers. Server owns identity, state, timestamps and permissions. Errors use existing `{code,message,correlationId,fieldErrors?}` with 401/403/404/409/422; body oversize 413. Unexpected fields rejected. Protected content `Cache-Control: no-store`.

- `GET /api/review-pool`: query `authorId?`, `minAgeDays?`, `maxAgeDays?`, `limit?`, `cursor?`. Age bounds nonnegative integers, minimum <= maximum, evaluated against server time/firstSubmittedAt. 20 default/100 maximum, ascending firstSubmittedAt then ID. Response `{items: PoolItem[], nextCursor}`. PoolItem contains `id`, `version`, `title`, `author:{id,username}`, `summary`, `firstSubmittedAt`, `latestSubmittedAt`, `awaitingRevision`; IDs/version are operational metadata for authorized claim. No full proposal state enum or hidden-content aggregates.
- Proposed assigned-list route (new internal choice, no conflicting approved route): `GET /api/reviews/assignments`, same filters/paging plus `state?` from eligible assigned lifecycle states. Always scoped to actor; return safe summary plus current assignment ID/revision ID/assignmentVersion/state for own records. In this increment meaningful live records are IN_REVIEW/CHANGES_REQUESTED; seeded completed states may be read to test frozen/disable behavior, without approval operations.
- `POST /api/proposals/:id/claim`: strict `{expectedVersion}`; no assignment ID exists yet and server selects current submitted revision. Return `{proposalId,revisionId,assignmentId,state,version,assignmentVersion}`. Never accept reviewer ID.
- `POST /api/proposals/:id/drop`: strict `{expectedVersion,revisionId,assignmentId,expectedAssignmentVersion}`; same committed command response, with closed assignment identity. Wrong current assignment/state/version yields 409 after role/access check; authenticated non-assignee 403. Missing objects 404 with safe envelope.
- `GET /api/proposals/:id?revisionId=...`: only implement Reviewer representation here; owner/Maintainer representations deferred, never accidentally exposed by a generic serializer. Current assignee receives proposal metadata, current assignment/version, selected submitted revision fields, immutable criteria/evidence, and a safe submitted-revision index. Omitted selector means latest. A revision from another proposal fails scoped retrieval. Owner/Maintainer support remains explicitly unimplemented rather than weakening their future specified permissions.
- `GET /api/proposals/:id/activity?cursor=...`: current assignee only in this slice, ordered 50-entry pages of allowlisted safe business events. No arbitrary metadata/request JSON. Preserve actor attribution; no operational or private AI records.

Claim/drop do not require idempotency keys under the approved integration policy. On uncertain response read current authorized state before offering a new action; do not resend blindly or silently reuse a different version.

## Persistence, transaction, and security contract

Use a PostgreSQL constraint guaranteeing at most one active assignment per proposal (partial unique index over active rows or equivalently constrained active pointer); also serialize on the proposal lifecycle root. Assignment rows preserve provenance and revision; drops/releases close a row rather than delete it. Proposal current-assignment pointer and active-row uniqueness are updated together and checked for consistency. Enforce current revision belongs to its proposal. Submitted snapshots are immutable through all available application operations; fixtures never update existing snapshots.

All assignment mutations revalidate enabled actor/role/account version inside the transaction, not only in IdentityGuard. Consistent lock order: actor account row, then affected proposal roots in stable ID order. Disablement uses the same order and transaction-aware release interface. Reads of full content use an authorization-consistent transaction: account then proposal locks/checks before loading protected relations, serialized with drop/disable. An already delivered response cannot be retracted; no later protected request is authorized after committed access loss. Browser clears its own protected state after observed loss and never lets obsolete response generations repopulate it.

Claim transaction: lock enabled actor then root, check expected root version, current revision/state and no active assignment, create historical active assignment, transition appropriate state, update pointer/version, append safe claim event, commit. Drop transaction: same locking, validate assignee/current assignment/revision/versions and eligible state, end assignment, clear pointer, transition appropriate state, increment versions, append event, commit. Disable transaction: lock account, disable/increment account version, lock unfinished assigned roots in ID order, close assignments/clear pointers and transition, append automatic-release events and account security event, commit; leave completed approval states untouched. Avoid standalone per-assignment commits or post-commit in-process activity hooks. Bound transaction waits; safely map conflicts without retrying arbitrary mutations.

Read projections whitelist fields rather than serialize Prisma objects. SQL filters and cursor application are scoped before paging. Parameterize all queries; cursors never authorize and unknown/tampered/oversized ones fail safely. Diff/evidence/summary render as text, not HTML or executable code. No external repository/code execution, AI calls, uploads, raw sensitive logging, new administrative web endpoints, credentials in fixtures, or business-event pruning.

Development/test fixtures use synthetic users and eligible submitted snapshots, including unassigned SUBMITTED/CHANGES_REQUESTED, assigned examples, multiple revisions/ages and frozen states for denial checks. Require explicit development/test configuration and production refusal, transaction and unique fixture keys; reruns preserve existing user changes/snapshots. Browser production-mode tests arrange fixtures through test-only direct DB setup before startup; no production HTTP seed path and no relaxation of fixture production guard.
