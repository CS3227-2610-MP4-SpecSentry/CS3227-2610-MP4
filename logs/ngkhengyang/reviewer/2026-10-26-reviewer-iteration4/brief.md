## Proposed API and persistence contract

1. `POST /api/proposals/:id/revoke-approval`: strict body `{expectedVersion, revisionId, assignmentId, expectedAssignmentVersion, approvalId, expectedApprovalVersion, reason, candidateContext}`. `expectedApprovalVersion` is the immutable decision's existing mutationVersion; no mutable approval row is invented. `candidateContext` is null for unattached, otherwise `{candidateId, expectedCandidateVersion}`. Null versus attached is checked against current locked state, so an old unattached form cannot silently become an attached revocation. Require original Idempotency-Key and CSRF. Reason: normalized line endings, nonblank, at most 2,000 Unicode code points; preserve submitted normalized text, escape output.
2. Authenticate and reauthorize assignment/access before replay, including current candidate scope for any stored attached result. Removal ending the Reviewer's candidate scope denies replay of that attached candidate result even if proposal assignment remains; authorized proposal history stays separately available. Key scope actor/operation/proposal; canonical hash includes every expected version/context/reason. Same live key/body returns original safe committed result even after its own state transition; changed body conflicts. Access loss denies replay. Retain 24h and reapply ordinary lifecycle/version checks after expiry. A fresh key against invalid approval conflicts.
3. Return committed proposal/assignment versions/state, effectiveApproval=false, invalidation provenance and candidate ID/version plus ONLY this assigned proposal's invalid-approval blocker when attached. Reviewer response, replay and direct candidate projections never include other members, aggregate readiness/gate failures, rollback/dependency notes or smoke text. Version the proposal and attached candidate general version on revocation; preserve candidate contentVersion and membership. Assignment identity/version stays unchanged unless its state actually changes. Read-only approval/invalidation history exposes original decision and attributed actor/time/reason/cause/revision/candidate to currently authorized viewers.
4. Extend ApprovalInvalidation with cause REOPENED/REVOKED and revocation reason/candidate reference, preserving old owner-reopen records through a migration default/backfill. Keep decisionId uniqueness and original decisions unchanged. Add validated same-proposal/revision/assignment/decision links and append-only protections consistent with existing migrations. Add APPROVAL_REVOKED and bounded release activity actions and candidate references to the safe activity allowlist.
5. Minimal release data: candidate OPEN/RELEASED, createdBy responsibility, metadata/general version and contentVersion; unique project semantic version; membership binds proposal/revision/approval with one active candidate per proposal; append-only smoke tests; immutable release snapshot. Convert/reconcile releaseAttachmentRef with real membership transactionally; legacy synthetic attachment rows are not upgraded into proof of release integration. Foundation owns fixture reconciliation and cleanup.
6. Minimal production API: candidate create, read detail/readiness, edit rollback/dependency/version metadata, add/remove member, append smoke test, publish. Only creator Maintainer mutates or publishes; other Maintainers read. Reviewer candidate reads are bounded to their assigned member context; never disclose unrelated members. Nonempty publish, semantic version, current revision/effective approval/required coverage/no HIGH-CRITICAL, rollback and current-content PASS smoke all gate publication. Membership changes advance contentVersion and invalidate old smoke tests. Publication writes immutable evidence, marks all members and candidate RELEASED and appends activities/idempotency atomically.
7. Extend notifications as a discriminated kind APPROVAL_REVOKED with candidate/proposal/reviewer/reason/invalidation provenance and exact recipient=createdBy. Use invalidation identity for uniqueness, not only revision. Preserve existing Reviewer visibility rules; Maintainer notices require current recipient and candidate scope. GET candidate detail is side-effect-free. After a successful authorized opening, the client explicitly POSTs each displayed notification ID to the existing acknowledgement route with session-bound CSRF and exact kind/candidate context; server rechecks recipient/candidate access and writes restricted read audit in that transaction. GET/prefetch alone cannot set readAt; opening the actual application page may intentionally trigger its own authorized POST. Acknowledgement never modifies approval, candidate version/contentVersion, smoke or blockers and never acknowledges a newer undisplayed notice. List/ack remains recipient-only and direct candidate read reauthorizes. Preserve notice reason/history after removal as authorized candidate evidence.

HTTP outcomes follow integration: 401 invalid/expired/disabled session, 403 authenticated role/object denial, 404 absent object without protected disclosure, 409 stale/state/gate/key conflicts, 422 invalid fields, 413 body cap, safe correlation envelope. Failed transactions leave no invalidation, business activity, notification, membership or snapshot fragments; separate safe rejection audit may remain.

## Proposed lock order and concurrent state protocol

All related operations use sorted relevant UserAccount IDs → actor AuthSession → ReleaseCandidate IDs sorted → ChangeProposal IDs sorted → assignment/approval/membership rows in stable ID order → append-only writes/idempotency. Resolve opaque candidate/responsible/reviewer pointers before locking, without returning protected fields; re-read under locks and conflict if discovered membership/account sets changed. Never acquire an additional account or candidate after holding proposal locks. Include notification recipient account before candidate to avoid FK/account-lock cycles with publication. Candidate responsibility is immutable.

Revocation locks actor plus attached candidate responsible account; removal ALWAYS locks Maintainer plus the current affected Reviewer before candidate/proposal, then determines unavailable-assignee recovery under those locks. A preliminary enabled check cannot waive that Reviewer lock. Publication locks its actor and candidate before reading the stable member set and locking every proposal in sorted order. All membership mutations take candidate before proposal; they cannot change the member set while publication holds candidate. Unattached revocation/reopen take accounts/session/proposal and never later request candidate locks. Existing proposal-only operations may finish or reject under their root lock and must never invert the new order.

Revalidate effective approval identity, revision, assignment generation, root/candidate versions and OPEN state after locks. Contributor reopen versus revoke has one lifecycle winner; attach versus unattached revoke cannot reinterpret old context; remove versus revoke either preserves attached blocker until removal or rejects stale context. If removal encounters a disabled Reviewer, apply the existing now-unfinished assignment-release semantics atomically rather than stranding CHANGES_REQUESTED. Disablement/session invalidation races must share actual locked identity/session rows; HTTP guard success is insufficient. Logout/store destroy lock behavior is part of independent review.

Revocation first: publication rechecks invalidation and fails without snapshot. Publication first: revocation sees RELEASED and fails without history mutation. Tests must hold controllable transaction barriers or observe PostgreSQL blocking; sequential calls or arbitrary sleeps cannot establish either ordering. A deadlock/serialization abort is a safe conflict with rollback, never an implicit retry with altered versions/key.
